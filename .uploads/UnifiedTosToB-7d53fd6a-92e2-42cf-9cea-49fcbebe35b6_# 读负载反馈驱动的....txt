# 读负载反馈驱动的数据放置调度方案

> 基于 `client_read_bandwidth_scheduler.cpp` 与 `worker_read_bandwidth_tracker.cpp` 及其实际调用链整理。源码基线：`6ea77da0`，核对日期：2026-09-11。本文描述当前实现的逻辑方案；后续建议单独列出，不代表已经实现。图使用 Mermaid，公式中 MiB = 1024² 字节。

## 1. 背景与方案定位

分布式缓存中的 Worker 既承接数据写入，也为后续读取提供数据。UB 端口部分故障后，Worker 可能仍然可用，但数据发送能力已经下降。继续将新数据集中放到该 Worker，可能加重后续读服务压力；无条件切换到其他 Worker，又会损失原有数据放置亲和性。

本方案将 Worker 的读数据回写耗时转换为可比较的读负载信号，在首选 Worker 出现已知 UB 坏端口时，结合各 Worker 的健康端口比例和读负载，调整后续单键写入的数据放置目标。

核心闭环为：**UB 读数据回写 → 有界采样 → 归一化 P50/P99 → Publish 响应反馈 → Client 候选评价 → 后续写入选点**。

这里的“读带宽”以固定数据量的传输耗时作为代理指标。当前方案不测量网卡剩余带宽，不进行令牌桶限速，不设置全局带宽配额，也不迁移已经存在的对象。它对后续读取的影响来自数据放置的变化，效果取决于后续访问分布。

### 1.1 目标

1. 在首选节点部分端口故障时，减少向高读负载、低可用传输能力节点继续放置数据的概率。
2. 在节点健康或端口状态未知时保留原路由，维持已有放置亲和性。
3. 用偏重尾延迟的指标识别慢节点，同时为符合准入条件的低权重节点保留被选择机会。
4. 限制采样、统计和候选选择的资源开销，使辅助调度不要求前台等待统计计算或新增探测 RPC。

### 1.2 当前实际覆盖范围

| 环节 | 当前接入范围 | 不能据此推导的能力 |
| --- | --- | --- |
| 负载采集 | QueryAndGet 的 UB 回写，围绕同步数据发送操作计时 | 全部 Get 端到端耗时、TCP/SHM 性能、磁盘读取耗时均被采集 |
| 反馈生产 | Worker 成功处理 Publish 后，将当前统计快照附在响应中 | 每次读响应都会携带统计信息 |
| 反馈消费 | Client 路由写入链路的 Set 成功后，按实际写入 Worker 更新本地统计 | 每个 Client 自动获取全体 Worker 的实时读负载 |
| 调度入口 | 单键选点，且放置策略为 `PREFERRED_META_OWNER` | 所有读写路径、所有放置策略均启用带权选点 |
| 批量路径 | 批量选点逐键执行原路由；读请求分组也使用该批量入口 | 批量 Set/Get 已获得同样的带权调度能力 |

“首选 Worker”指原路由经过排除列表和可用性过滤后给出的目标，并不保证一定是对象键在哈希环上的第一个归属节点。

```mermaid

    U --> S[成功样本筛选与大小归一化]
    S --> H[有界历史窗口]
    H --> P[后台计算 P50 / P99]
    P --> F[成功 Publish 响应携带快照]
    F --> C[Client 按 Worker 保存读负载]
    T[拓扑更新] --> L[候选 Worker 集合]
    V[UB 健康快照] --> D[Client 调度决策]
    C --> D
    L --> D
    W[后续单键写入选点] --> A[原路由给出首选 Worker]
    A --> D
    D --> O[向选定 Worker 放置数据]

```

### 2.1 模块分工

| 逻辑模块 | 输入 | 输出 | 职责边界 |
| --- | --- | --- | --- |
| Worker 读耗时采集 | UB 回写开始、完成、数据大小、成功状态 | 有效归一化样本 | 记录传输阶段，不决定路由 |
| Worker 统计器 | 有配额的样本 | P50、P99、统计版本 | Worker 进程级汇总，不按对象、租户或 Client 拆分 |
| 反馈通道 | Worker 当前统计快照 | Publish 响应附带字段 | 复用业务响应，不单独广播 |
| Client 负载状态 | 实际目标 Worker 的反馈 | 延迟成本、更新时间、版本 | 维护性能信号，不维护 UB 故障事实 |
| 拓扑候选管理 | 路由拓扑中的 Worker 集合 | 有界候选表 | 控制候选身份与生命周期，不预先聚合全体权重 |
| UB 健康与可用性过滤 | 已发布健康快照、外部过滤规则、排除列表 | 健康比例与准入判断 | 故障证据由既有健康模块管理 |
| 选点决策 | 首选目标、候选成本与健康情况 | 最终 Worker | 先亲和判断，再防饥饿或带权抽样，最后回退 |

## 3. 端到端业务时序

读负载可以由不同 Client 的请求产生；接收 Publish 反馈的 Client 只得到该 Worker 的汇总视图。图中的读请求与写请求不要求来自同一个调用者。

```mermaid

    participant W as Worker
    participant T as 读负载统计器
    participant BG as 统计后台线程
    participant WC as 写请求方 Client
    participant S as Client 调度器
    RC->>W: QueryAndGet，经 UB 返回数据
    W->>T: 记录回写开始
    W->>RC: 同步 UB 数据回写
    W->>T: 完成：耗时、字节数、成功状态
    T->>T: 筛选、配额、归一化、写入历史
    opt 当期成功入窗样本达到配额
        T->>BG: 标记需要刷新
        BG->>T: 轮询发现标记，计算并发布分位数
    end
    Note over T,BG: 后台异步计算；前台不等待刷新
    WC->>W: 后续一次写入的 Publish
    W->>T: 读取当前统计快照
    W-->>WC: 成功响应 + P50 / P99 / 版本
    WC->>S: 更新该 Worker 的本地成本
    Note over WC,S: 反馈只影响后续选点，不改变已完成写入
    WC->>S: 再次单键写入，需要选择 Worker
    S->>S: 原路由首选 → 健康判断 → 必要时带权选择

```

反馈延迟由“样本形成时间 + 统计刷新等待 + 下一次成功 Publish 等待 + 响应处理”共同决定。由于 Publish 可能长期不发生，当前链路没有固定的端到端反馈时延上界。

## 4. Worker 侧：从回写耗时到读负载

### 4.1 样本采集流程

```mermaid
flowchart TD
    A[UB 回写开始，记录单调时钟] --> B[执行同步回写并记录完成]
    B --> C{启用、有效、成功且数据至少 256 KiB？}
    C -- 否 --> Z[结束，不增加统计样本]
    C -- 是 --> D{耗时大于零且当前周期还有配额？}
    D -- 否 --> Z
    D -- 是 --> E[折算为 4 MiB 对应耗时]
    E --> F{历史槽位可写且样本仍有效？}
    F -- 否 --> Z
    F -- 是 --> G[发布样本到有界历史窗口]
    G --> H{当期成功入窗数量达到上限？}
    H -- 否 --> Z
    H -- 是 --> I[设置后台刷新标记]
    I --> J[后台读取有效样本，计算分位数]
    J --> K[发布 P50 / P99 并递增版本]
```

样本不包含回写计时之前的查找、锁获取等全部业务阶段，因此不能当作业务 Get 延迟。失败请求不进入分位数，失败风险需要结合 UB 健康与业务错误信号观察。当前调用不传实际队列深度，默认记录为 1；队列深度不参与归一化和调度公式。

### 4.2 数据量归一化

设一次成功回写的数据量为 $D$ 字节，耗时为 $t$ 纳秒，基准数据量为 $D_0=4\times1024^2$ 字节，则归一化耗时为：

$$
L=\max\left(1,\left\lfloor\frac{tD_0}{D}\right\rfloor\right)
$$

极大值按整数容量饱和处理。该公式将不同大小请求折算到同一数据量，避免单纯因为对象大就被判断为更慢。例如，2 MiB 用时 300 μs，对应 4 MiB 归一化耗时 600 μs；8 MiB 用时 800 μs，对应 400 μs，因此后者的单位数据传输效率更高。

在近似线性传输模型下，可用下式解释等效带宽：

$$
B_{\mathrm{eq}}=\frac{D_0\times10^9}{L}\quad\text{字节/秒}
$$

这是解释指标含义的换算，当前调度直接使用耗时，不计算该带宽。如果原始耗时包含固定启动成本 $a$，即 $t=a+D/B$，则 $L=aD_0/D+D_0/B$。这说明归一化仍受对象大小影响；256 KiB 下限可以减少小对象固定成本的干扰，但不能完全消除它。

### 4.3 有界采样与历史窗口

默认采样周期 $\Delta=1$ ms，每个周期最多申请 $Q=4$ 个采样名额：

$$
k=\left\lfloor\frac{\mathrm{完成时间}}{\Delta}\right\rfloor,
\qquad n_k\le Q,
\qquad r_{\mathrm{sample}}\le\frac{Q}{\Delta}=4000\ \text{样本/秒}
$$

采样名额按完成时刻竞争，并非均匀随机抽样。名额申请成功后，槽位冲突导致的丢样不会补回名额；实际入窗数量可以更少。

历史容量默认 $H=1000$。窗口按最近的写入序号范围维护，读取时跳过无效、被覆盖或未稳定发布的槽位，因此有效统计样本数 $N\le H$。它是样本窗口，不是严格的时间窗口。只有在持续满配额且写入成功时，1000 个样本约覆盖 250 ms；低负载时可以跨越更久。

**刷新条件尤其需要区分：后台定期轮询，不等于后台定期无条件计算。** 当前只有某一周期成功入窗数达到 $Q$，才设置刷新标记。默认每周期不足 4 个样本且没有其他待处理刷新标记时，分位数可能长期不更新。达到配额后，默认后台约每 1 ms 检查标记，但线程调度不提供硬实时保证。

### 4.4 P50/P99 计算

将有效归一化耗时按升序记为 $L_{(1)},\ldots,L_{(N)}$，采用最近秩定义：

$$
P_q=L_{(\lceil qN/100\rceil)},\qquad q\in\{50,99\}
$$

例如 8 个样本为 200、220、240、260、300、350、400、900 μs，则 P50 为第 4 个值 260 μs，P99 为第 8 个值 900 μs。小窗口下 P99 接近最大值，不能将其视为已经得到充分样本支撑的长期尾延迟。

统计计算使用选取分位点的方式，无需完整排序。每次发布后版本递增。P50/P99 在响应中各为 32 位无符号纳秒数，最大约 4.295 秒，超出时饱和。冷启动使用 P50=200 μs、P99=500 μs、版本=0；这组值是先验值，不是实测结果。

## 5. Client 侧：反馈状态与候选维护

### 5.1 反馈接收规则

Client 按 Worker 地址保存最近收到的合法 P50/P99。零值、P50 大于 P99、空 Worker 地址的反馈被忽略；反馈更新竞争激烈时也可能跳过一次更新。

当分位数变化时重新计算亲和与非亲和成本；即使数值相同，正常接收的反馈也会刷新本地接收时间和记录版本。默认超过 100 ms 未刷新时，状态查询显示不新鲜，但当前选点仍使用已有成本。

这里有两个不同的时间概念：

| 概念 | 表示什么 | 当前能否严格保证 |
| --- | --- | --- |
| Client 接收新鲜度 | 最近多久收到合法反馈 | 可由本地时间判断 |
| Worker 测量新鲜度 | 分位数来自多久以前的样本 | 响应没有携带样本时间，无法严格判断 |

重复返回旧统计快照，也可能使 Client 接收时间看起来很新。统计版本当前作为记录字段使用，不用于拒绝乱序或低版本反馈，不应描述为严格的版本防回退协议。

### 5.2 候选集合维护

候选来源是路由拓扑中的 Worker，默认最多维护 16384 个状态槽。拓扑通知触发候选刷新，默认设置 60 秒最小刷新间隔；它不是独立的每 60 秒刷新定时器。在间隔内到达的更新会跳过，因此新拓扑何时进入调度候选，还依赖后续通知。

候选表采用两份有界快照交替发布。一次选择固定使用一个候选快照和一个 UB 健康快照，避免在选择中反复读取变化的全局集合。离开当前候选集合的状态，满足不活跃时间且不被读者使用后才允许回收；槽位复用带身份代际校验。

## 6. Client 侧：选点规则与流程

### 6.1 调度进入条件

算法开关默认关闭。启用后，只有单键 `PREFERRED_META_OWNER` 路径接入该策略，先由原路由产生首选 Worker，再读取其 UB 端口健康情况：

- 状态未知或没有坏端口：保留原路由结果，包括原状态码。
- 存在已知坏端口：进入候选调度。

因此，健康 Worker 即使 P99 已很高，也不会单凭延迟触发切换。“延迟门限”用于进入调度后的候选准入，不是独立切换触发器。

### 6.2 主决策流程

```mermaid
flowchart TD
    A[单键放置请求] --> B[原路由：排除列表与可用性过滤后产生首选]
    B --> C{目标策略且调度已启用？}
    C -- 否 --> O[返回原路由目标和状态]
    C -- 是 --> D[固定本次 UB 健康快照]
    D --> E{首选存在已知坏端口？}
    E -- 否 --> O
    E -- 是 --> F{存在可读取的候选表？}
    F -- 否 --> X[回退首选，保留原路由状态]
    F -- 是 --> G[最多检查两个防饥饿候选]
    G --> H{符合防饥饿及全部候选准入？}
    H -- 是 --> S[记录选中时间并返回目标]
    H -- 否 --> I[均匀抽候选，按成本与健康比例接受]
    I --> J{通过准入、概率接受与可用性过滤？}
    J -- 是 --> S
    J -- 否 --> K{抽样与过滤拒绝预算允许继续？}
    K -- 是 --> I
    K -- 否 --> X
```

选中不同于首选的候选时，路由返回成功；回退首选时保留原路由状态。调度内部的回退分支不会重新检查首选的排除列表、端口状态或过滤器，因此“返回首选”不等于重新证明其可用，更不等于业务 RPC 成功。正常链路的首选已经经过原路由过滤，但并发健康变化仍由后续准入和业务错误处理承担。

### 6.3 候选准入规则

| 条件 | 正常带权选择 | 防饥饿选择 |
| --- | --- | --- |
| 候选身份有效、没有被复用 | 必须 | 必须 |
| 不在本次排除列表和已拒绝集合中 | 必须 | 必须 |
| 已知健康端口数大于零 | 必须；未知健康状态按健康因子 1 处理 | 相同 |
| 延迟成本有效，P99 不超过门限 | 必须 | 必须 |
| 外部可用性过滤通过 | 必须 | 必须 |
| 按权重概率接受 | 必须 | 不需要 |
| 满足防饥饿时间条件 | 不需要 | 必须 |

防饥饿不能绕过全端口故障、超延迟门限和外部过滤。旧统计仍可选，不会因为超过 100 ms 就自动清零权重。

## 7. 关键计算公式与原理

### 7.1 尾延迟加权成本

记 Worker 的归一化分位数为 $P_{50}$、$P_{99}$，非亲和惩罚为 $\delta=200$ μs，则：

$$
C_i=\left\lfloor\frac{P_{50,i}+3P_{99,i}}{4}\right\rfloor
    +\begin{cases}0,&i\text{ 为首选 Worker}\\\delta,&\text{其他 Worker}\end{cases}
$$

P99 占 75%，使尾部变慢比中位数变慢更明显地降低吸引力。非亲和惩罚表达偏离首选的固定成本偏好，并不是逐次测得的额外网络耗时。

P50/P99 为零，或 P99 严格大于门限 $G$ 时，成本视为无效，不能进入正常候选选择。正常初始化时：

$$
G=\left\lfloor\frac{T_{\mathrm{request,ms}}\times10^6}{1000}\right\rfloor\times600
\ \text{ns}\ \approx 0.6T_{\mathrm{request}}
$$

例如请求超时设为 20 ms，门限为 12 ms；P99=12 ms 可准入，P99>12 ms 不可准入。调度器未由正常初始化设置门限时，内部默认也是 12 ms。

注意：门限比较对象是“归一化为 4 MiB 的 P99”，所以它只是性能保护阈值，不能保证任意大小实际请求都在超时前完成。

### 7.2 健康比例与平滑反比权重

设 Worker 总端口数为 $n_i$，坏端口数为 $b_i$，则健康因子：

$$
h_i=\frac{n_i-b_i}{n_i}
$$

健康信息未知或无有效端口计数时按 $h_i=1$ 处理；已知全部端口故障时为 0。这里按数量比例衡量能力，没有区分不同端口的容量差异。

参考延迟 $R=1000$ μs，权重刻度 $S=10^6$。有效候选的逻辑吸引力为：

$$
a_i=\frac{R}{R+C_i}\times h_i
$$

用于状态展示的整数权重为：

$$
w_i=\max(1,\lfloor Sa_i\rfloor)
$$

无效成本或全端口故障时直接取 $w_i=0$。正常支持宽整数的选点路径直接用 $a_i$ 做接受判断；整数权重是等价趋势的展示量，极小概率及兼容计算路径存在取整差别。

分母中的 $R+C_i$ 使吸引力处于有界范围：低延迟节点不会出现无限大的权重；当成本远大于 $R$ 时，吸引力近似按 $1/C_i$ 下降。健康端口从 4 个减为 2 个，在成本不变时吸引力减半。若端口故障已经推高 P99，两个因素会叠加惩罚；当前没有针对这种相关性做消除处理。

### 7.3 带权拒绝采样

每次先从 $M$ 个候选中近似均匀抽一个，再独立生成接受随机数，以 $a_i$ 接受该候选。未通过随机接受仅表示这次未命中，不会把该 Worker 加入拒绝集合。

在候选和过滤结果稳定、忽略防饥饿与有限预算等影响时，成功选中条件下的相对概率为：

$$
\Pr(i\mid\text{抽样成功})\approx\frac{a_i}{\sum_j a_j}
$$

每次选择最多执行 100 次带权抽样，避免为了找到低概率候选无限循环。默认可用性过滤拒绝预算为 3 个不同候选，拒绝集合容量最多 16；它与“抽样 100 次”是两种不同预算，不代表业务 RPC 重试次数。

设全部候选的平均有效接受率 $\bar a=\sum_i a_i/M$，在独立稳定近似下，连续 $K$ 次均未选出的概率为：

$$
P_{\mathrm{miss}}\approx(1-\bar a)^K
$$

当平均接受率只有 1% 时，100 次仍未命中的概率约为 36.6%。所以有限抽样回退是正常边界，不能将最终整体流量比例直接等同于权重比例。

随机序列由请求键、Client 盐值和递增选择序号共同生成。同一个键不会总选中同一个 Worker；Client 盐值默认为空，当前初始化也没有为其自动注入独立身份，因此不能保证多个同序请求 Client 之间充分去相关。

### 7.4 防饥饿选择

设当前时间为 $t$，最近选中时间为 $t_s$，最近反馈接收时间为 $t_r$，最近强制选中时间为 $t_f$，保护间隔 $T_s=1000$ ms，则满足下列任一条件可进入防饥饿候选：

$$
(t-t_s\ge T_s)\quad\lor\quad(t-t_r\ge T_s\ \land\ t_f<t_r)
$$

每次进入调度时，轮转检查最多两个候选。符合条件并通过准入的节点可以跳过概率接受，直接被选中；并发认领约束减少多个线程同时强制选择同一节点。

它提供的是随业务调度发生的机会，不是主动探测，不保证每个 Worker 每秒得到请求。若首选始终健康，调度不进入该阶段；若节点因过高 P99 被排除，防饥饿也不能使其获得一次恢复性试探。

### 7.5 综合数值算例

假设首选 A 有 1 个坏端口而进入调度。三台 Worker 均通过过滤，无防饥饿命中，门限为 12 ms，数据均已归一化为 4 MiB：

| Worker | 角色 | P50 / P99（μs） | 健康端口 | 成本 C（μs） | 接受率 a | 条件相对概率 |
| --- | --- | --- | --- | --- | --- | --- |
| A | 首选 | 200 / 500 | 3/4 | 425 | 0.526316 | 37.98% |
| B | 非亲和 | 200 / 500 | 4/4 | 625 | 0.615385 | 44.41% |
| C | 非亲和 | 400 / 1000 | 2/4 | 1050 | 0.243902 | 17.60% |

上表相对概率以三个接受率之和 1.385603 归一化，仅描述稳定条件下的带权抽样结果。显示值因四舍五入不一定恰好合计 100%。

B 虽有 200 μs 非亲和惩罚，但完整健康端口带来的优势超过了惩罚；A 仍然可能被选中，说明“进入调度”不等于“强制离开首选”。若 A 没有坏端口，则在入口直接保持 A，上述概率根本不会参与本次决策。

## 8. 端口退化与恢复时序

```mermaid
sequenceDiagram
    participant H as 既有 UB 健康模块
    participant R as Client 路由
    participant S as 带权调度器
    participant A as 首选 Worker A
    participant B as 候选 Worker B
    H-->>R: 发布 A 的已知坏端口情况
    R->>R: 单键写入原路由仍给出 A
    R->>S: 使用同一健康快照判断是否保留 A
    S->>S: 已知部分坏端口，进入调度
    S->>S: 防饥饿检查；未命中则带权抽样
    alt 成功选中 B
        S-->>R: 返回 B
        R->>B: 执行写入
        B-->>R: 成功 Publish + B 的读负载
        R->>S: 更新 B 的成本
    else 没有选出替代目标
        S-->>R: 回退 A
        Note over R,A: 保留原路由状态，业务准入和请求仍可能失败
    end
    H-->>R: 发布 A 所有端口健康
    R->>S: 下一次单键写入判断
    S-->>R: 保持原路由首选 A
```

恢复证据来自 UB 健康模块；读负载统计不自行宣布端口恢复。由于健康快照可以独立更新，端口恢复不必等待新的 P50/P99；反过来，只有延迟数据过高而长期无反馈时，没有独立的主动刷新机制保证成本恢复。

## 9. Use Case

| 编号与场景 | 前置条件 / 触发 | 主流程与预期结果 | 边界与观察点 |
| --- | --- | --- | --- |
| UC-01 正常亲和放置 | 单键目标策略，首选无坏端口 | 原路由直接保持首选 | 即使候选更快，也不触发带权比较 |
| UC-02 部分端口故障 | 首选 1/4 端口坏，其他节点可用 | 进入调度，结合成本和健康比例选点 | 首选仍有非零概率，不保证每次转移 |
| UC-03 慢候选降权 | 已进入调度，某候选 P99 上升但未越门限 | 75% 尾延迟贡献提高成本，降低接受率 | 这是降权，不是故障隔离 |
| UC-04 候选超门限 | P99 大于 G | 正常与防饥饿阶段均拒绝该候选 | 若候选也是最终回退首选，回退分支不复核 |
| UC-05 全端口故障 | 已知候选全部端口坏 | 候选权重为零，不经候选阶段选中 | 还需区分原路由过滤与最终回退语义 |
| UC-06 节点长期未选中 | 已进入调度，候选超过 1 秒未选中，且满足准入 | 轮转探测命中时跳过概率接受 | 无流量时不会主动请求该节点 |
| UC-07 新 Worker 加入 | 拓扑通知到达且满足刷新间隔 | 建立候选状态，以 200/500 μs 先验参与 | 默认值不证明真实能力；候选接纳可能延迟 |
| UC-08 长期纯读或低写负载 | Worker 有读样本，但 Client 没有成功 Publish | Worker 可能更新统计，Client 继续使用已有状态 | 读请求分组本身也不执行该调度；闭环不能保证收敛 |
| UC-09 小对象或低采样密度 | 数据小于 256 KiB，或每周期入窗不足 4 个 | 前者不采样；后者不单独触发统计刷新 | 区分没有测量、测量未发布、反馈未送达 |
| UC-10 候选过滤拒绝或抽样耗尽 | 候选不可用、表为空或概率未命中 | 有界退出并回退首选 | 记录回退原因；返回目标不等于执行成功 |
| UC-11 端口恢复 | 健康模块发布首选无坏端口 | 下次单键选点恢复保持首选 | 不要求等待负载统计刷新 |
| UC-12 批量 / 同节点策略 | 批量选点，或非目标放置策略 | 沿用原路由 | 不能将单键测试结论推广到这些路径 |
| UC-13 进程重启 | Worker 或 Client 重建 | 丢弃本地历史，以先验和新拓扑重建 | 版本可能从零开始，没有持久化迁移 |

### 9.1 UC-02：部分故障下的后续放置调整

**参与者：**写请求 Client、原路由、UB 健康模块、读负载调度器、多个 Worker。

**前置条件：**两端已启用功能，使用目标单键放置策略，候选表已建立，首选仍通过原路由可用性过滤，但健康快照显示存在坏端口。

1. 原路由给出首选 A。
2. Client 固定本次健康快照，识别 A 的部分故障，进入调度。
3. 优先检查少量防饥饿候选；没有命中时进行带权抽样。
4. 假设选中 B，向 B 执行既有写入流程。
5. B 成功 Publish 的响应携带 B 的读负载，Client 更新 B 的状态。

**后置条件：**本次数据按既有写入语义放置到 B；A 上已有对象不移动。新数据位置对后续读分布的影响，需要端到端实验确认。

**异常分支：**没有替代节点时回退 A；B 写入失败时不在本模块内部重新循环选点，沿用既有业务错误处理与重试约束。

## 10. 性能、并发与恢复设计约束

### 10.1 热路径开销

Worker 前台增加计时、筛选、原子配额竞争和单槽写入，统计计算在后台执行，不额外复制对象负载。固定样本数组限制内存增长，但多个发送线程共享配额计数和写序号，仍可能产生原子竞争与缓存行抖动。后台扫描及分位点选取也会消耗 CPU 和缓存带宽。

Client 预计算延迟成本，健康比例在本次选择时读取。抽样探测使用有界缓存，避免同一次选择重复解析相同候选；没有为了每次请求重新扫描全体 Worker 并求权重总和。但原路由搜索、哈希槽查找、外部过滤、Worker 地址复制以及诊断日志仍有成本，不能把整个请求路径宣称为严格 O(1)、零分配或无竞争。

默认 Worker 样本量不超过 4000 次/秒，Client 每次最多 100 次带权抽样、2 个防饥饿探测。候选构建与槽位回收在拓扑控制路径执行，仍需观察其对前台共享缓存与并发读取的影响。

### 10.2 共享状态的所有权与可见性

| 状态 | 所有者与生命周期 | 保护与读取原则 |
| --- | --- | --- |
| 样本历史、统计临时空间 | Worker 进程内统计器 | 多生产者写单槽，后台读有效序号；争用时允许丢样 |
| P50/P99 快照 | Worker 统计后台发布 | 两个分位数成对发布；版本单独发布，不应理解为完整事务快照 |
| Worker 延迟成本 | Client 路由持有的调度器 | 单槽更新串行化，选点读预计算原子状态；允许并发观察到近邻更新 |
| 候选集合 | Client 拓扑控制路径 | 双表发布、读者持有期间不改写该表、身份代际校验 |
| UB 健康快照 | 既有健康注册与验证模块 | 调度器持有不可变快照；过滤器自身仍可能读到更晚的状态 |
| 防饥饿时间与认领 | Client 调度器 | 原子认领与时间更新，降低并发重复强制选中的概率 |

同一个读计时令牌要求最多完成一次，统计器没有业务请求去重表。调度器析构前调用方应停止并发访问；Worker 统计器停止并等待后台线程退出后才释放资源。候选刷新与回收遵循既有读者保护协议，不能在读者持有旧表时随意覆写槽位身份。

### 10.3 持久化、重启与失败处理

这些状态是性能提示，保存在进程内存，不写 WAL、ETCD 或磁盘；没有新增部分落盘、压缩或持久化清理流程。进程重启后以先验值重新开始，不恢复旧采样窗口或 Client 权重。对象数据的持久化、一致性和故障接管仍由原有存储与元数据链路负责。

允许丢弃采样和使用旧反馈，但不因此获得更强的业务可用性保证。反馈附在成功响应中不增加新的业务写操作；调度器不执行 RPC 重试，不改变既有写入幂等性契约。重试选点可能因序号、健康状态或反馈变化而得到不同目标，必须服从既有重试语义。

建议先在可控负载中对比关闭与启用两组，覆盖不同对象大小、读写比例、端口退化程度与 Worker 数量。扩展范围前，由 Client 路由、UB 传输与健康、Worker QueryAndGet/Publish 相关维护者共同核对业务效果。回滚关闭功能并重建实例，不涉及数据格式回退；已放置的数据仍按既有位置管理。

## 12. 可观测性、验证与待完善项

### 12.1 观察闭环是否真正工作

| 要回答的问题 | 当前证据入口 | 判读方式 |
| --- | --- | --- |
| 是否采到有效读回写 | Worker `RBS_W` 的 READ / SAMPLE | 区分成功读、获取配额与后续有效入窗；SAMPLE 日志本身不保证槽位写成功 |
| 是否形成新统计 | Worker `WINDOW_END` | 查看有效样本数和 P50/P99；没有窗口日志时检查配额与刷新条件 |
| Client 是否收到反馈 | Client `RBS_C` 的 OBSERVE | 看接收的版本、分位数和成本变化，不只看更新时间 |
| 为什么进入或保持亲和 | Client 决策入口日志 | 结合首选的坏端口计数 |
| 选中来源与回退 | Client 决策结果日志 | 区分带权、防饥饿与 `fallback_preferred` |
| 候选状态是否退化 | `SLOT_TABLE_DEGRADED` | 关注墓碑比例、长探测及拓扑变化 |

Worker 的 READ、SAMPLE、WINDOW_END 使用详细日志级别 VLOG(1)，Client 的 OBSERVE、DECIDE_ENTRY、DECIDE_FINAL 当前使用 INFO。Client 决策与反馈日志因此也是功能启用后的前台成本，不能只通过关闭详细日志就认为已消除记录开销；性能对比必须固定日志配置。

### 12.2 验证建议

现有单测源文件覆盖了大小归一化、样本忽略条件、窗口分位数、配额、并发历史覆盖，以及候选排除、超门限、全端口故障、防饥饿、过滤拒绝和回退等行为。这是静态检查到的测试范围，本次文档任务没有执行这些测试，也不据此宣称性能或并发安全已经实测通过。

面向方案验收，建议补足以下端到端证据：

1. 在“成功 UB 读回写 → 统计刷新 → 成功 Publish → Client 观察 → 下一次单键选点”上关联日志，证明完整反馈闭环。
2. 对比纯读、低频写、每周期不足采样配额，确认旧统计与旧反馈的实际持续时间。
3. 在部分端口故障、恢复、全候选拒绝时，核对真实业务返回码，不能只断言调度函数返回目标。
4. 分别验证单键、批量和同节点策略，防止把覆盖范围理解错误。
5. 测量开关前后的业务 P50/P99、吞吐、CPU、原子竞争和回退比例；性能基线与日志级别保持一致。

### 12.3 当前边界与后续建议

| 当前边界 | 影响 | 后续建议，尚未实现 |
| --- | --- | --- |
| 仅成功 Publish 反馈 | 纯读和低写负载 Client 可能长期无新信息 | 评估读响应携带或复用既有控制通道；先明确额外开销 |
| 仅当期样本满配额触发刷新 | 低负载统计可能不更新 | 评估有新样本时的最长刷新间隔 |
| 接收时间不等于测量时间，版本不做防回退 | 旧快照可显得新鲜，乱序反馈可覆盖新值 | 评估样本年龄、Worker 实例身份与版本联合语义 |
| 健康未知按因子 1 | 不完整信息可能让未知节点更有吸引力 | 用冷启动与故障实验评估未知状态权重 |
| 高延迟节点不能靠防饥饿越过门限 | 缺少反馈时可能难以重新准入 | 评估独立、限额的恢复探测，避免绕过硬故障准入 |
| 拓扑刷新有间隔且无独立补偿定时器 | 候选加入与剔除可能滞后 | 评估拓扑版本变化时的刷新语义 |
| 只接入目标单键选点 | 批量和读路径不共享该策略 | 扩展前明确是写放置优化还是读副本选择，分别设计 |
| 默认 Client 盐值为空 | 同序 Client 的选择可能相关 | 评估稳定且不暴露敏感身份的实例扰动 |
